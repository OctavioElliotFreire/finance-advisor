# Family Finance — Agent Instructions

FastAPI/Postgres/Supabase backend in `backend/`, Flutter frontend (web/Android/iOS) in `frontend/`. See `PLAN.md` for architecture and milestone history.

The repo originally also kept an old Streamlit/SQLite MVP running at the repo root alongside this rewrite. It was retired 2026-07-28 once the new stack's first vertical slice was verified end-to-end against the real Pluggy sandbox API (see `PLAN.md`'s "First Vertical Slice" section) — don't re-create root-level `app.py`/`db.py`/`sync.py`/`llm/`/`pages/` files; that's dead architecture now.

## Verification Policy

Never mark a task or response as complete without validating the actual output in this session — not "should work" from reading the code, not a claim carried over from a previous turn.

- **When an automated test covers the change**: run it, in this session, and only report success after it actually passes. If it fails, fix it or say so — don't paper over a failure.
- **When no automated test covers the change**: say so explicitly, and describe the manual verification performed instead (a curl/TestClient call and its actual output, an import/smoke check, a migration up/down round-trip, a `flutter test`/manual click-through). Never silently skip verification.
- **Never claim something works without having executed it.** A passing type-check or successful import is not the same as a passing behavioral test — don't conflate them.

This is about agent behavior before declaring work done. It's distinct from `PLAN.md`'s "Testing Strategy" section, which describes what test *coverage the product* should eventually have — don't duplicate that here.

## Known test surfaces

| Surface | Command | Notes |
|---|---|---|
| `backend/` (FastAPI/Postgres) | `docker compose up -d db` then `cd backend && source .venv/Scripts/activate && python -m pytest tests/ -q` | Tests hit a real Postgres via `DATABASE_URL` and mutate rows directly (create/query/delete `app_users`, `households`, `household_members`). Default to local Docker Postgres, not the live Supabase project, so repeated runs don't mutate shared dev state. `.env`'s `DATABASE_URL` does not point at local Docker Postgres — override it explicitly on the command line (see Lessons Learned below), never edit `.env` to fix this. |
| Alembic migrations | Round-trip: `alembic upgrade head` → `alembic downgrade -1` → `alembic upgrade head`, against local Docker Postgres | Catches things autogenerate gets wrong that a single `upgrade` won't — e.g. a Postgres enum type created by `create_table` but not dropped by the generated `downgrade()`. Do this before considering any new migration correct. |
| `frontend/` (Flutter) | `flutter test` | Real coverage exists now: repository/data-layer tests, auth/household widget tests, and (as of the chart work below) unit tests for each chart's `*_data.dart` mapper plus widget tests for each `*_chart.dart` (populated/empty/single-point/single-category fixtures) under `test/ui/features/{dashboard,finances}/widgets/`. A pass is meaningful for what it covers — it still isn't full end-to-end coverage (no integration test drives a real login → sync → chart-render path), so keep pairing it with the manual QA in `MANUAL_TESTING.md` for anything that crosses that boundary. |

## Browser Testing: `expect` vs `playwright-cli`

Both skills touch browser automation and their trigger wording overlaps ("test", "verify", "QA", "web pages") — split by artifact so they don't compete for the same task:

- **`playwright-cli`** owns anything that produces or runs a *persistent* test file — its `test-generation` reference does plan/generate/heal of committed `.spec.ts`-style tests, and its `playwright-tests` reference runs the existing suite. This is the tool for building out real E2E coverage that would earn a row in Known Test Surfaces above.
- **`expect`** owns the *ephemeral* post-change QA gate only — open → click through → audit (console/network/a11y/perf) → close, producing a pass/fail report but no files kept. Use it for "did this fix actually work" checks, not for building a suite.
- `expect`'s own README says "always use me over Playwright MCP/raw browser tools" — that instruction is **overridden** here for anything that authors or runs a committed test file; route those to `playwright-cli` instead.
- **Flutter Web gotcha (applies to both):** the CanvasKit renderer paints to `<canvas>`, not semantic DOM. ARIA-tree snapshots/refs (`ref('e5')`, `accessibility_audit`) may find nothing unless the build has semantics enabled or uses the HTML renderer — confirm a snapshot actually contains the expected elements before trusting it. Also see the `flutter run -d web-server` hang note below — it applies to both tools' headless runs.
- **`expect` MCP confirmed working 2026-08-03** after the `SKILL.md` rename + `.mcp.json` `expect-mcp` bin fix (see Lessons Learned below) — tools `open`/`playwright`/`screenshot`/`console_logs`/`network_requests`/`accessibility_audit`/`performance_metrics`/`close` all resolve and function. Two Flutter-Web-specific quirks hit during that first real run, both worth knowing before the next `expect` session:
  - The "Enable accessibility" placeholder button (`flt-semantics-placeholder`) sits at `(-1,-1)` size `1x1` — a normal Playwright `.click()` times out with "element is outside of the viewport". Use `await (await page.$('flt-semantics-placeholder')).dispatchEvent('click')` instead.
  - `ref('e1').fill(...)` does not reliably register with Flutter's `TextField` (CanvasKit intercepts input events) — it can silently no-op or apply to the wrong field. Use `ref('e1').click()` then `page.keyboard.type(text, {delay: 30-80})` per field instead; fast delay can also drop characters, so prefer ~50-80ms and verify the snapshot shows the full string before submitting.
  - `accessibility_audit` on a Flutter Web CanvasKit page always reports several "serious" IBM-engine violations (`html_skipnav_exists`, `skip_main_exists`, `style_color_misuse`, `aria_keyboard_handler_exists`/`widget_tabbable_single` on any tablist) — these are inherent to the renderer, not app regressions; don't treat them as new bugs unless they change between runs. A couple of `svg_graphics_labelled`/`text_block_heading` findings pointing at `expect`'s own on-page overlay (the audit/perf toast) are tool artifacts, not app issues — ignore selectors outside the `flutter-view`/`flt-*` tree.
  - `performance_metrics` measures from initial page load, not from the last navigation — on a long-lived Flutter Web SPA session (hash-routing, no reloads) LCP/INP will look artificially "poor" because they're timing the whole multi-minute session, not a fresh render. Close and reopen the browser right before measuring if a real per-view metric is needed.

## Lessons Learned

Every time a mistake happens in this repo, add the rule that prevents it here — don't let the same error recur across sessions.

- **Postgres passwords with special characters (`@`, `+`, `/`, etc.) break `DATABASE_URL` parsing.** A raw `@` in a Supabase DB password got misread as the user/host separator, silently mangling the hostname and failing DNS resolution. Percent-encode special characters in connection-string passwords, or — simpler — recommend an alphanumeric-only DB password for local/dev use to avoid the whole class of bug.
- **Supabase free-tier auth email sending is rate-limited project-wide, not per-address**, and repeatedly returns `429 over_email_send_rate_limit` on normal `POST /auth/v1/signup` calls during testing. Toggling "Confirm email" off in the dashboard does not necessarily clear an already-tripped limit. For any dev/test user creation, use the Admin API instead: `POST {SUPABASE_URL}/auth/v1/admin/users` with headers `apikey: <service_role_key>` and `Authorization: Bearer <service_role_key>`, body `{"email", "password", "email_confirm": true}` — creates an already-confirmed user with zero emails sent. Then sign in via `POST /auth/v1/token?grant_type=password` (anon key) for a real access token.
- **Alembic autogenerate creates a Postgres enum type via `create_table` but never drops it in the generated `downgrade()`.** A migration adding a `sa.Enum` column will fail on a second `upgrade` after a `downgrade` with "type already exists" unless fixed. Always add `sa.Enum(name='<enum_name>').drop(op.get_bind(), checkfirst=True)` to `downgrade()` for any migration that adds an enum column, and confirm with the upgrade → downgrade → upgrade round-trip described in Known Test Surfaces above.
- **`backend/.env`'s `DATABASE_URL` does not point at local Docker Postgres.** Running `alembic`/`pytest` with no override silently hits the wrong database or fails with a confusing connection error (looked like a resolved-to-a-remote-IPv6-address failure once). Always export `DATABASE_URL="postgresql+psycopg://finance_app:local-development-only@localhost:5432/family_finance"` explicitly for local commands instead of relying on or editing `.env`.
- **FastAPI backend had no CORS middleware** — any browser-hosted Flutter Web build got blocked talking to it from a different origin/port. Fixed by adding `CORSMiddleware` in `app/main.py` driven by `settings.cors_allowed_origin_regex` (defaults to any `localhost` port; override via `.env`'s `CORS_ALLOWED_ORIGIN_REGEX` in production). If real-browser testing of Flutter Web ever breaks again with a CORS console error, check this config before assuming it's a Flutter bug.
- **`flutter run -d web-server` hangs forever in a plain headless-Chromium session** (no Dart Debug Chrome extension installed) — it injects a DWDS debug client that waits on an extension handshake that never completes. Looks identical to a silent app-boot failure. For headless/Playwright verification, use `flutter build web` and serve `build/web` with a plain static server instead.
- **`flutter build web` alone compiles `AppConfig.supabaseUrl`/keys as empty** — the app has no hardcoded fallback, so every login POSTs to the static file server's own origin (e.g. `http://localhost:8901/auth/v1/token`) instead of Supabase, failing with a generic `501`/"Something went wrong" with no obvious cause. Always build with `flutter build web --dart-define-from-file=.env` for any real-login manual/browser QA. Also: a stale static server process serving the old `build/web` will silently keep the broken compile alive after a rebuild — stop it and restart against the fresh `build/web` before re-testing.
- **The web build's "Connect institution" flow is an intentional stub** (`frontend/lib/ui/features/connections/views/connections_view.dart` `_connect()`) — it shows a snackbar ("...use the mobile app for now") instead of launching Pluggy Connect. Don't treat this as a bug; it means seeding fresh synced data for web-only QA must go through the backend API directly (Pluggy sandbox auth → create item → `POST /v1/households/{id}/connections` → run `python -m app.workers.sync_worker`), not through the web UI.
- **Local Docker Postgres app data does not persist across sessions the way Supabase Auth does** — `manual-test@example.com` still existed in Supabase Auth but had zero households in a later session, because the local Docker Postgres volume had been reset/recreated. Don't assume a previously-seeded household/connection is still there; check `GET /v1/households` first and reseed if empty.
- **`gemini-flash-latest`'s dynamic "thinking" tokens share the same `max_output_tokens` budget as the visible answer, and can silently eat the whole thing.** With no `thinking_config` set, a real production call (via `app/llm/providers/gemini.py`'s `answer_question`, `max_output_tokens=600`) returned a garbled, mid-sentence-truncated answer (`": ELETROBRAS...\n- 2026-06-10:"`) with **no error** — `finish_reason` only surfaces the problem if you check it (`MAX_TOKENS` instead of `STOP`), which nothing did. Root cause confirmed by direct SDK calls: `thoughts_token_count` varies per-call and can approach/exceed the budget on its own before the model even starts the visible answer. Fix: always pass `thinking_config=types.ThinkingConfig(thinking_budget=<fixed value comfortably under max_output_tokens>)` (e.g. budget 512 with `max_output_tokens=1024`) so thinking can never crowd out the answer, and always check `response.candidates[0].finish_reason == types.FinishReason.STOP` before trusting `response.text` — raise instead of returning a truncated string. This class of bug is invisible in code review and in a single lucky manual test; only showed up on a repeat real call. Anthropic's `stop_reason` should get the same treatment (`in ("end_turn", "stop_sequence")`) since it doesn't have this specific failure mode by default but the "trust finish reason before trusting text" principle is provider-agnostic.
- **go_router on Flutter Web reads the browser's actual current URL at construction time — the `GoRouter(initialLocation: ...)` constructor param does NOT override it.** Building the household-invite-link feature, landing on Supabase's raw redirect (`http://host/?invite=xxx#access_token=...&type=invite`) threw `GoException: no routes for location: /access_token=...` — go_router parsed the fragment itself as a route path before any app code ran, regardless of an `initialLocation` passed into `buildRouter()`. Fix: for any deep-link-style entry point, rewrite the address bar to a clean, resolvable route via `html.window.history.replaceState(null, '', cleanPath)` **before** `runApp()`/`buildRouter()` executes (see `frontend/lib/core/web/invite_redirect_cleanup_web.dart`, gated behind a conditional import — `dart:html` isn't available on the mobile targets this repo also ships, so stub it with `if (dart.library.html)`). `initialLocation` alone is not sufficient on web.
- **A Supabase user gets lazily created in our own `app_users` table on their very first authenticated backend request — even one from a never-completed flow.** During QA, an invite recipient's session got applied (`applyInviteSession`) but the accept step never ran (due to the go_router bug above); that alone was enough for `get_current_app_user` to create an `AppUser` row for their email. Re-inviting the same email afterward silently took the "existing user, add directly" branch instead of sending a fresh invite email — correct per the code's logic (an `AppUser` row exists → not a stranger), but surprising during testing. Don't assume "never logged in" == "no `AppUser` row"; check `app_users` directly if an invite behaves like the email was already known.
- **`expect-cli`'s `mcp` subcommand crashes on Windows with `Cannot find module 'C:\C:\Users\...\browser-mcp.js'`.** Root cause: `dist/index.js`'s `mcp` command resolves its target script via `new URL('./browser-mcp.js', import.meta.url).pathname`, which on Windows yields a leading-slash path like `/C:/Users/.../browser-mcp.js`; that string is then passed through `path.resolve()`-equivalent logic, which on `win32` treats the leading `/` as "root of the current drive" and prepends the cwd's drive letter again, producing `C:\C:\Users\...` (reproduced directly: `path.resolve('/C:/Users/...')` → `C:\C:\Users\...`). This is a bug in the `expect-cli` npm package itself (confirmed present in 0.1.3, the only recent release line), not fixable in this repo's code. **Workaround:** the package also ships a separate `expect-mcp` bin (`dist/browser-mcp.js` directly, bypassing the buggy path join) — point `.mcp.json` at that instead of the `mcp` subcommand: `{"command": "npx", "args": ["-y", "-p", "expect-cli@latest", "expect-mcp"]}`. Also check `claude mcp list` for a stale duplicate `expect` entry in **user** scope (`claude mcp remove expect -s user`) shadowing the project one — conflicting scopes silently keep the broken endpoint active even after `.mcp.json` is fixed. Either way, an MCP config change never takes effect mid-session (needs a fresh session + approval), so don't expect the fix to unblock the current conversation.
- **`PluggyClient`'s bare `httpx.AsyncClient()` calls (no explicit timeout) intermittently hit httpx's 5s default against the real Pluggy API**, and the resulting unhandled 500 has no CORS headers — a browser hitting this reports it as a CORS error, not a timeout, hiding the real cause. Hit this building the web Connect widget (2026-08-05): a real `/auth` call took 4.8-8s from this dev machine. Fixed with `REQUEST_TIMEOUT = 30.0` applied to every `httpx.AsyncClient()` in `backend/app/sync/pluggy_client.py`. If a browser console ever shows a CORS error on a call that has no obvious cross-origin config change behind it, check the backend server log for the actual exception before trusting the browser's diagnosis — an unhandled exception anywhere will look like CORS from the browser's side.
- **A test fixture's teardown that hits a foreign-key violation aborts its ENTIRE transaction, silently leaking every row that teardown was supposed to delete — not just the one that failed.** Adding the `audit_events` table (FK to `households`, deliberately not `ON DELETE CASCADE` — see `PLAN.md`'s Milestone 10 notes) broke ~4 test files' teardown fixtures that delete `households` directly without first deleting `audit_events` rows referencing them: the delete raised `ForeignKeyViolation`, and since all the fixture's earlier deletes (household members, connections, etc.) were part of the same uncommitted transaction, Postgres rolled all of them back too. This had apparently been happening for a while across unrelated bugs (56 orphaned `app_users` rows accumulated in local Docker Postgres, including duplicates, by the time this was caught) — a fixture teardown that errors doesn't just fail loudly, it leaves the local test database permanently dirtier than before the run, and subsequent runs then fail for a *second*, unrelated reason (stale data colliding with fresh test data, e.g. an email that "shouldn't" already have an `app_users` row). Fix applied: every test fixture that deletes a household must delete every table with a FK to `household_id`/`household_member_id` first, in dependency order, including new tables added later — and if a full suite run ever shows failures that don't reproduce for a test run in isolation, suspect leaked cross-run data before suspecting new logic. Recovery when this happens: query for rows whose values don't match any real/intentional fixture (test emails, not `manual-test@example.com` or other named QA fixtures — see `MANUAL_TESTING.md`), and delete them in the same dependency order.
- **`docker cp`'s destination argument gets mangled by git-bash's MSYS path auto-translation** on Windows: `docker cp local-file.sql finance-advisor-db-1:/tmp/purge.sql` silently rewrites the container-side `/tmp/purge.sql` into a Windows-style path, and the subsequent `docker exec ... psql -f /tmp/purge.sql` then fails with a Windows path in the error message despite running entirely inside the Linux container. Same root cause as the `expect-cli` Windows bug below (MSYS treats any argument starting with `/` as a POSIX path to translate, even when it's meant for a remote/containerized filesystem). Fix: prefix the command with `MSYS_NO_PATHCONV=1` for both the `docker cp` and the following `docker exec`.
- **Pluggy's Connect widget defaults `includeSandbox` to `false` on both platforms** (the web `pluggy-connect-sdk` and the `flutter_pluggy_connect` mobile package) — neither `PluggyConnectScreen` (mobile) nor the new web widget set it, so the connector picker silently showed only real/production connectors, no sandbox "Pluggy Bank". Selecting the one real connector shown opened a genuine third-party Auth0 login — caught before entering any real credentials. Now controlled by `AppConfig.pluggyIncludeSandbox` (defaults `true`); must flip to `false` via `.env`'s `PLUGGY_INCLUDE_SANDBOX` before real bank connectors go live. If a Pluggy Connect widget session ever shows unexpected real-bank connectors during dev/QA, check this flag first.

## Permission Boundaries

- **Autonomous** (no need to ask): `docker compose up -d db`; running migrations against local Docker Postgres; running the root/`backend/` test suites; read-only queries against the live Supabase Postgres; additive `alembic upgrade head` against the live Supabase project; creating and cleaning up throwaway Supabase Auth test users via the Admin API within the same session (per the Lessons Learned pattern above) — as long as no pre-existing real user is touched; normal source edits, still governed by the assistant's standing global git-safety rules.
- **Ask first**: `docker compose down -v` (deletes the local dev Postgres volume); `alembic downgrade` run against the live Supabase project; deleting, disabling, or modifying any real (not created this session) Supabase Auth user, table, or project setting; `git push` / force-push / branch deletion — this repo has no CI, so a bad push has no safety net catching it.
- Global hard-blocks (force-push to `main`, `--no-verify`, etc.) already apply and aren't repeated here.
